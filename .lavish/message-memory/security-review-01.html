What runs where

The local listener reads the Messages database on the M4. An additional M5 backfill covers history available there. The Macs retain their original Messages databases.

Capture rule

Your own inline #tag saves that message. A reply with #tag, 🔖, or 📌 saves the explicitly linked parent message. That parent can have been written by someone else. Supported custom reactions can use the same save/pin mapping.

URL fragments do not count as tags. Missing reply linkage goes to review; the listener does not guess the preceding message. Native Apple content pins are not imported.

What the backfill means

About 3,200–3,300 capture events were staged per Mac. These counts overlap and are not a count of unique messages or people. Coverage is limited to history actually present on each Mac.

A historical hashtag is a candidate capture, not proof you intended to upload it. Reviewing candidates before enabling bulk import is a remaining product step.

What is stored, and what would leave the Mac

The initial proposal uploads selected message content, not just a link back to Messages. That distinction is central to this review.

Access boundaries and their limits
On the Mac
  • Messages is opened read-only; capture does not alter chat.db.
  • The SQLite archive uses private filesystem permissions. It is not separately encrypted by this feature.
  • The M4 service uses an existing Python installation that already has Full Disk Access. That permission is broad, not restricted to Messages.
  • Local archive and contact data are outside Git. Logs are intended to contain counts and fixed errors, not message bodies.
External-volume encryption, backup inclusion and retention have not been verified in this work.
Proposed server boundary
  • A dedicated device credential can ingest captures for one owner. It cannot browse the archive or send messages.
  • Only its hash is stored server-side; the local credential file requires private permissions.
  • Archive reads and export require the owner’s direct signed-in OpenChat session. Embedded sessions and general agent connectors are excluded.
  • Revocation blocks future device ingestion. Previously imported records remain until deleted.
A stolen ingest key can still submit false data. Database operators and sufficiently privileged server access can read plaintext captures. Backup copies require their own retention policy.


Deletion has several separate layers
  • Forget in OpenChat: removes that capture’s payload and retains a tombstone to prevent replay from restoring it.
  • Thread/contact snapshot: may remain independently; forgetting one message is not a complete contact-data purge.
  • Local outbox: separate from server deletion. A polished local purge/review workflow is not built yet.
  • Original Messages and Apple Contacts: remain in their source apps. This feature does not delete them.
  • Account deletion: proposed cleanup removes the owner’s capture, thread and device records. Backup deletion is a separate operational question.


“Local archive only” has a specific meaning
No bulk import of this staged archive has been sent to OpenChat. Archive generation runs on your Macs. Some targeted source messages were inspected through agent tools to carry out your Drew/Roger requests; “local-only archive” is not a claim that no message content ever appeared in this agent session.
The explicit Apple Contacts address and door-code writes are already complete. Those contacts may sync according to your existing Apple/Google contact-account settings; this work did not change those settings.


Saving, tagging and sending are separate
The listener does not send acknowledgements or messages when it captures something. Replying with a hashtag inside iMessage is a real message visible to that conversation; tagging privately in the proposed app is different. The CLI’s explicit send command delegates to the installed iMessage tool, but this task has not sent messages.
WhatsApp capture, shared item audiences and public publishing are design proposals. The current capture implementation is private. Person → tag and All saved → tag remain the organizing model.

Issues the code review found
Fixes address embedded-session export access, invalid records blocking uploads, destination changes on later saves, service restart/configuration, confidentiality checks for direct additions and manual tags, contact field labels, and concurrent upload acknowledgements. Review and validation are still in progress.




Decisions before any database import
  1. Which captures: selected people/items first, or a reviewed historical hashtag backfill?
  2. How much content: full selected messages and trigger text, or a smaller/redacted representation?
  3. Contact snapshots: keep Apple Contacts fields on-device, or sync approved fields into OpenChat?
  4. Sensitive information: define local-only categories and an explicit review queue; heuristic detection alone is insufficient.
  5. Storage and retention: choose encryption/backup expectations and a clear local + server purge workflow.
