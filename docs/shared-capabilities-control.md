# Shared Control/OpenChat capabilities v1

Implementation owner Control Sol f7ade329. OpenChat tickets OpenChat-3dsp and OpenChat-vwgq.2; isolated branch feat/control-shared-capabilities. No Earmark source edits.

The assistant derives a scope from current membership and conversation type. Only the owner's exact two-participant direct assistant DM can be universal. Every group/inline turn is conversation-scoped; the tools catalog is filtered and execution independently denies any private-source/new tool and foreign target. Searches filter on conversation before retrieving results and omit global semantic search. Isolated conversation turns expose read tools only: send_message/post_context are denied even with model-supplied confirm:true; the assistant can still answer as itself. Pending human-send proposals are keyed by user AND originating private assistant conversation, never injected into another scope. Every call rechecks membership; a DM that becomes shared loses universal authority. The requested `assistantScope` is persisted through REST, socket and outbox transports; it can narrow, never expand, the server-derived authority of a turn. Composer usage is documented in [the README](../README.md#assistant-context-and-save-to-vision). The shared send boundary snapshots the selected chat scope and destination together for text, photos, files/captions, and emoji before asynchronous preparation; recordings retain their scope from start through upload even if the composer changes. Each delayed assistant trigger carries its persisted originating message ID, validates chat/actor/membership, derives authority from that message, and bounds context to it. The same persisted message boundary constrains origin-chat tool reads, keyword and semantic searches, and conversation previews throughout the model loop; universal reads of other authorized chats remain available. Other messages sharing its timestamp are conservatively omitted. Quoted reply ancestry is server-resolved, membership-filtered, bounded to three levels/3000 excerpt characters and cycle-protected. Unavailable ancestors expose no metadata. Existing replyToId transport remains canonical. Quoted and third-party context never grants scope or write confirmation; the owner's universal private DM retains model-mediated confirmation for human sends.

`POST /api/vision/connection` starts/reuses an owner-consented Vision-only personal connector grant. The key stays encrypted on the server using the existing OC_KEY_ENCRYPTION_SECRET with per-owner authenticated encryption. The response includes connection status and, when approval is needed, an approval URL and comparison code; it never returns the credential. See [connection usage](../README.md#assistant-context-and-save-to-vision). This reuses existing `/agent/keys/request`, `/agent/keys/status` and `/mcp`; no new write proxy or built-in secret is needed. `/builtin-agent/read` remains read-only. Neither a native ID token, an email match, nor service-key possession establishes Vision write authority.

`POST /api/vision/saves` uses the authenticated human's local identity (no client/model owner field), with the request and receipt types owned by [the save service](../apps/server/src/services/visionSave.ts) (`SaveRequest`, `SaveReceipt`, `parseSaveRequest`). `sourceRefs` must contain nonempty OpenChat message references; request limits are enforced by `parseSaveRequest`. Each source ref supplies `sourceDigest`, the lowercase SHA-256 of the full message content (or transcript if content is empty). New writes require matching digests and current membership, rechecked after grant validation and reservation immediately before dispatch; excerpts must still be actual substrings. Legacy versionless requests are accepted only for matching historical receipt lookup, never a new dispatch. Versioned payload hashes include the digest; matching legacy receipt hashes remain readable by upgraded clients. Grant issuer+subject must exactly match the persisted local identity and read/write permissions are checked fresh. No agent/model tool can invoke this human Save route. Current ordinary connector write does not accept an idempotency key: server stores the attempt before dispatch, embeds an opaque provenance marker in the note body, and only reports saved after persisting a durable destination ID. A duplicate key returns its existing receipt, a different payload is rejected, and lost destination/ledger acknowledgments retain the original uncertain receipt. An explicitly confirmed new copy uses a fresh UUID and current authority; the original is never silently retried. Existing matching owner receipts are returned before rechecking source/linkage/grants, so deleting a source or revoking a grant cannot erase a prior saved receipt. New saves/copies always recheck current source ACL and grant. A reserved attempt records a server-owned phase and selection hash. Only an acknowledged transition from its owned reservation to `rejected_before_dispatch` proves non-dispatch; legacy, missing, reserved, dispatching, saved, uncertain and unacknowledged outcomes do not qualify. `POST /api/vision/saves/review` reads that durable proof and current source ACL, retains the selected body, rejects missing excerpts, and returns refreshed digests for review without writing a note. The [review flow](../README.md#assistant-context-and-save-to-vision) requires two explicit actions before generating a fresh UUID. That save carries `retryOf`, rechecks proof, owner identity, source digests and Vision grants, and atomically links only one successor per rejection. The old receipt is preserved; a timeout cannot authorize recovery, and a successor with unknown outcome cannot be bypassed by reusing the old rejection. An upgraded conflicting digest still rejects the old payload but can offer this review when the selected content matches durable evidence. Nothing automatically retries an uncertain write. WikiHub/Noos writes are unavailable.

A saved result requires a real note ID; returned destination URLs must use the exact Vision origin, otherwise the receipt falls back to the Vision home page. Uncertain receipts, including historical reservations, expose the searchable opaque `openchat-save:` marker. The route also returns HTTP 503 with an uncertain receipt when ledger acknowledgment fails. The mobile request decoder preserves that response in `ApiError` (still re-exported from `api/client.ts`); the real Save catch presenter passes its reason to `uncertainVisionAlert`, preserving the marker and duplication warning. Malformed or non-uncertain failures keep the conservative receipt-unavailable fallback. The message action currently submits whole-message text or exact selections as `excerpt`; the service types define the other accepted kinds. No real user note/message is used as a test.
