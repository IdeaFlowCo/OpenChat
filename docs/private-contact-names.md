# Private contact names

For set/edit/clear instructions in the native and responsive web client, see [private contact names in the client README](../apps/mobile/README.md#set-a-private-contact-name).

`GET /api/private-names/:id/profile` also returns a minimal official `{ id, name, avatarUrl, isBot }` projection after the same authenticated visibility check. It contains no email, phone or private name and does not require a conversation. When the viewer and target are accepted friends (an `accepted` `OpenChatConnection`), it adds `card`: the target's active AddMe card projected exactly as a card-link holder sees it (`projectCardForStranger`, so each `show*` flag is honoured and no token, id or email is included). Every other viewer gets only the four fields above.

The server stores a directed `OPENCHAT_PRIVATE_NAME` relationship from the authenticated viewer’s `User` to the canonical target `User`. `GET`, `PUT`, and `DELETE /api/private-names/:id` derive the owner exclusively from the signed-in session; caller-supplied owner identifiers are ignored. `GET` returns `{ name: string | null }`; `PUT` accepts `{ name: string }` and returns the trimmed name; `DELETE` returns `{ name: null }`. Names must be nonempty after trimming, at most 100 UTF-16 code units, and free of C0 control characters, DEL, and Unicode line/paragraph separators; invalid input returns 400.

Profile reads, alias reads, and sets return 404 for missing, self, bot, or targets blocked in either direction. Otherwise the target must allow name discovery, be discoverable by an exact email supplied by the viewer, share a conversation with the viewer, or have a pending/accepted friend connection with them. For an `email_only` target without a friend connection or shared conversation, send the complete email used to discover them, URI-encoded in the `X-OpenChat-Discovery-Email` header on profile reads, alias reads, and sets. The server normalizes and checks it against the target's email; malformed URI encoding returns 400. This proof does not grant access to `hidden` targets or bypass mutual blocks, and the response never returns the email. Sets and clears acquire the same ordered user locks as block/friend mutations. An owner can always delete their own metadata, including after a block or visibility change; deletion is idempotent, needs no discovery proof, and never reveals target information. Imported/unlinked device contacts have no canonical OpenChat user ID and cannot receive an alias.

Private names are fetched through this dedicated authenticated, uncached endpoint and kept in account-scoped client memory, remounted when the viewing account changes. They do not replace `User.name` or any conversation/title payload and are never passed to cards, vCards, QR codes, share links, exports, notifications, or search projections. Official-name updates therefore retain the alias’s canonical target without overwriting the current official label. Collection and retention disclosures are owned by the [privacy policy](../apps/server/src/legal/privacy.md).

Regression coverage lives in `apps/server/test/privateNames.route.test.ts`, `privateNames.integration.test.ts`, `privateNames.mobile.test.ts`, and `groupOpen.mobile.test.ts`. The integration suite requires all of `NEO4J_TEST_URI`, `NEO4J_TEST_USER`, and `NEO4J_TEST_PASSWORD` pointing to a disposable database; otherwise it skips. CI provisions that database in `.github/workflows/mobile-chat-regressions.yml`. Physical iPhone VoiceOver/keyboard acceptance remains a separate live-device gate.
