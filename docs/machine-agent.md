# Pair a device to a machine agent

In the installed OpenChat app, open **Chats › Machine agent**. Give the OpenChat account ID and public device key to the operator of your computer over a channel you already trust. The operator compares the whole key, chooses one newly created, unused, dedicated Paseo agent and workspace, and returns a private offer. Paste it into **Private machine offer** and select **Pair device**. Keep the offer out of chat messages, logs, URLs and screen recordings.

**Send to machine** opens a private request. The operator sees the exact text and approves it in the machine terminal. **Check last turn** retrieves the encrypted receipt after a disconnect. When delivery is uncertain, inspect the dedicated Paseo agent before repeating a request. **Forget device key** removes the key from this app account. The machine operator can revoke the grant independently.

## Machine operator

Use the reviewed checkout, its pinned npm dependencies, Node 22.13 or later and the separately reviewed Paseo revision listed under Verification. The installed SDK and daemon must both implement local approved-turn operation version 2. The CLI reports an unsupported installation before offering a pairing. Set `OPENCHAT_PASEO_SDK` to the absolute path of that installation's `packages/client/dist/index.js` and `OPENCHAT_PASEO_PORT` to its local TCP listening port. The bridge connects to IPv4 loopback. A daemon that requires a password uses the operator's established local `PASEO_PASSWORD` mechanism. Use a dedicated agent that nobody else messages and a workspace suitable for the approved consumer. The adapter checks its exact UUID, canonical working directory, idle state, provider and pinned mode before every send. Supported Codex modes are `auto` and `read-only` where the installed daemon offers it. The operator sees the selected mode when granting access.

Run these commands from the OpenChat repository. Run `offer` and `serve` in an interactive terminal. The arguments below contain only the public device key, route and local scope.

```sh
node scripts/machine-agent/host.mjs offer DEVICE_PUBLIC_KEY AGENT_UUID /absolute/workspace OPENCHAT_ACCOUNT_ID
node scripts/machine-agent/host.mjs serve ROUTE
node scripts/machine-agent/host.mjs list
node scripts/machine-agent/host.mjs revoke ROUTE
```

The offer command asks for local approval and saves the private offer in a mode-0600 file under the owner's mode-0700 state directory under the local daemon home (`~/.paseo/openchat-machine` by default). For a nondefault daemon home set `OPENCHAT_PASEO_HOME` to its exact directory. It prints the path. Deliver the contents privately. The offer expires after 10 minutes. A grant lasts 24 hours. The foreground listener deletes consumed or expired offer files. A copied file becomes unusable after activation or expiry. Each grant permanently owns its agent ID. A replacement grant needs a fresh unused agent. Protocol v2 pairs one machine per native app account. Daemon restart or provider-session replacement requires a new grant and fresh agent.

The operator confirms each prompt separately. The existing provider may use tools allowed by its local configuration and show its normal approval prompts. A working directory selects the agent's workspace. OS accounts, filesystem permissions, provider sandbox settings, configured connectors and secrets determine the actual filesystem and network boundary. An operator who needs strict filesystem isolation should give that agent a suitably isolated account or container. The machine bridge has no authority to approve provider prompts.

The bridge commits a local reservation before contacting Paseo. The daemon commits a submission fence, checks the exact operator-approved text digest, request ID, expiry, agent, workspace, mode, queue, session and timeline, and submits one literal turn directly to the provider. Its final admission check and provider write share a synchronous revocation boundary. The scoped Codex request pins user-reviewed approvals and an explicit read-only or workspace-write sandbox. Slash commands are refused. The provider's accepted turn ID must bind both the user message and returned assistant text. Local permission prompts remain local.

Revocation blocks new work and receipt retrieval as soon as the ledger commits. The daemon removes the exact queued item when applicable, interrupts only the recorded active turn, checks settlement and inspects the remaining queue. A provider or process failure can leave work outstanding. An unconfirmed interruption returns a nonzero CLI status and keeps the agent quarantined across restarts. Inspect the dedicated agent locally. Revocation cannot undo effects that have already occurred.

## Protocol and threat model

The mobile device creates a Curve25519 keypair with Expo Crypto's native CSPRNG. SecureStore holds the secret key, pending offer and request counter under the local account. On iOS the keychain item uses `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. Secure storage failure stops pairing. The machine keeps its identity, individual grant pins, offer hash and durable request record in an owner-private SQLite database. A machine persists one identity across devices. Identical account credentials on another handset do not reproduce the device key.

The bridge uses TweetNaCl's Curve25519/XSalsa20-Poly1305 box with independent random 192-bit nonces and rejects all-zero Diffie–Hellman results. The authenticated plaintext contains the versioned protocol label, grant/session routing ID, both public keys, direction and request contents. Replies bind both a counter and a random request ID. A status check uses a fresh challenge and names the original request inside the ciphertext. Device keys and the machine public key are exchanged out of band. Relay messages cannot replace either pin. Activation also requires the local one-use secret and proof of the pinned device key.

The mobile app advances its sequence before sending. On the machine a SQLite transaction reserves the new sequence, authenticated contents hash and request ID before terminal review. High-water marks reject older sequences. Repeated delivery of the current message retrieves its existing receipt. A higher sequence can skip a lost request. A higher sequence cannot displace a request under review or in flight. Only the most recent receipt is retained. An interrupted dispatch has an explicit uncertain outcome. Retry never causes a second provider dispatch of that request. A machine backup restored to an earlier point must use a new identity and new grants before reconnecting.

The v2 relay registers a route only after a direct signed-in device presents its own random ticket, the intended account ID through its signed login, the expiry and the machine ticket hash. The route commits to both ticket hashes, the account and expiry. The machine joins a registered route with its separate 256-bit ticket. Possession of the routing ID cannot claim either endpoint. The relay applies a limit of eight registered routes per authenticated principal and 2,000 in the process, endpoint exclusivity, rate and frame limits, hard grant expiry and idle eviction. It handles ciphertext and transport metadata. An attacker controlling the relay can read the relay tickets, interrupt delivery or suppress receipts. Local cryptographic device pins, the independent activation secret and local per-turn consent still govern commands. Groups, forwards, automatic replies and chat history have no machine dispatch path.

Keep the client and machine independently trusted. Web users see native pairing instructions. A compromised web origin could use even a non-extractable browser key while its page was open. Native OS signatures authenticate the installed app. EAS project access, OTA delivery and the contents of a native update remain trusted unless an independent publisher certificate is embedded and checked by the binary. The 1.0.20 app config has no Expo Update code-signing certificate. Per-message terminal consent is therefore mandatory. A malicious client update could steal app-readable device keys or capture plaintext; the terminal's independent review remains essential. Full compromise of the target GCP host, user account or local daemon can change policy or read keys and ends the protection. Static device keys do not provide forward secrecy. The selected provider receives the approved plaintext and Paseo can retain local history.

## Design sources

Paseo's relay uses TweetNaCl box, checks for low-order keys, and pins the machine key in its connection offer. Its paired transport exposes a daemon API broader than OpenChat needs. This bridge exposes one bounded agent message and a receipt. [Paseo relay source](https://github.com/tmad4000/paseo/blob/135a3b4c9e49a28b9d16ced8fc0e45b4da9fc502/packages/relay/src/crypto.ts)

The private Chat Coach host binds a browser key with a short-lived machine-generated secret and protects traffic with directional replay checks. Its host security notes also document hosted-page trust and copying results into server history. OpenChat keeps results in its machine view. Buzz uses a session-bound pairing transcript and an out-of-band comparison. OpenChat's operator compares the full device public key and passes the machine offer out of band. [Buzz pairing transcript](https://github.com/tmad4000/buzz/blob/73cc31cc528318debedd38e85d67b79d1feb55e8/crates/buzz-core/src/pairing/crypto.rs) · [Chat Coach host security at the reviewed revision](https://github.com/IdeaFlowCo/chat-coach/blob/646ccecb5454af38547566aa650f25f72c4fc38b/docs/host-security.md)

The native cryptography requirement is secure random bytes. The box implementation is JavaScript and the existing Expo modules provide random bytes and secure storage. A Linux Expo export produces distributable JS and Hermes assets. Installed-client execution and update acceptance require a device receipt. Adding an independent Expo Update signing certificate requires a new native build and runtime. [Expo SDK 54 Crypto](https://github.com/expo/expo/tree/sdk-54/packages/expo-crypto) · [Expo Update code signing](https://docs.expo.dev/eas-update/code-signing/)

The local RPC pins each approved request to the Codex thread sent in its JSON-RPC request and the native turn ID in the correlated start acknowledgment. It buffers up to 64 relevant early notifications. Only a completed agent message and a terminal notification with both matching IDs can produce the encrypted answer. Revocation targets the same pair and requires an observed terminal status. A lost acknowledgment, ambiguous identity, disconnected transport, or unsupported version leaves the agent reserved for local inspection. Upgrading a ledger from the earlier protocol revokes its grants and clears cached results. Start with a fresh dedicated agent and new local consent.

## Verification

CI exercises device and scope substitution, wrong tokens, expiry, duplicate activation, interrupted requests, reordered and replayed ciphertext, revocation, private result extraction, direct-session relay authentication and the actual mobile service through a local socket relay. The native-service test substitutes secure storage and randomness at the platform boundary.

The required Paseo source is `db87bf6e2246748deef7136be032e98413b07025` on the fleet fork. Set `PASEO_TEST_SOURCE` to that clean exact checkout and `PASEO_TEST_INSTALL` to its built distribution, then run `node --import tsx scripts/machine-agent/paseo.e2e.mjs`. The fixture starts a private daemon, loopback relay and deterministic provider in a temporary home. It exercises the actual CLI through a pseudo-terminal, declined and accepted enrollment, declined and accepted turns, repeated distinct messages, scope/expiry checks and an uncertain revocation. It uses synthetic keys and temporary storage. The installed Jacob device, real provider, production update and existing shared daemon each require separate verification.


### Relay ingress

Set `OPENCHAT_TRUSTED_PROXY` to the single, verified IP address of the nginx container on the actual ingress network. The server reads this value after loading its environment. Express and the machine relay both use this immediate-hop pin. An unset value leaves it using the transport peer. Bind the address, network identity and nginx header policy together and rebind before address changes or reuse. Nginx must replace incoming X-Forwarded-For with its verified peer or append its observed peer at the right. Verify any upstream real-IP rewrite independently. Only that immediate pinned hop supplies one address for the sampled `machine_relay_admission` denial event. The event omits tickets, routes and message data. It is emitted at most once per five seconds per process. Anonymous namespace connections still receive `Relay admission unavailable`.

Capacity is shared by authenticated owner and process. Different users behind a shared ingress can each register up to eight routes. Changing addresses cannot create room for a full principal. The global pool can fill if enough distinct authorized accounts register, subject to grant and idle expiry. Direct clients, Docker gateways and co-tenants receive no forwarded-address trust from sharing a private range. The same pin governs Express client IP and forwarded protocol/host attribution. A direct request to port 4001 must record its transport peer in the existing api_auth security event. Check normal HTTPS URL generation, auth audit and rate-limiter behavior through the bound nginx path on both origins before release.
