## Current OpenChat contract, disabled

OpenChat's test harness is at `/api/connector-delegations`, mounted only when `OPENCHAT_CONNECTOR_DELEGATION_ENABLED=true`, `NODE_ENV` is not `production`, and an exact HTTPS callback allowlist and client secret are configured. No client or production callback ships enabled. The store is in-process, so the production version needs a durable atomic code/grant store before activation.

1. Relying-party backend calls `POST /api/connector-delegations/start` with Basic client authentication and JSON `{callback, connectorGrantId, connectorUserId, expectedOpenChatUserId?, scopes, state, codeChallenge}`. `scopes` is a subset of `openchat.read`, `openchat.send`; send implies read. Callback must equal a registered full URL. State is RP-generated random data. Challenge is base64url SHA-256 of a 43–128 character PKCE verifier. Response has an opaque `transaction` and `reviewPath`; it contains no bearer credential.
2. Browser signs into OpenChat by its existing supported session. `GET reviewPath` with the OpenChat user JWT returns client, connector account, OpenChat user and requested scopes. It binds the transaction to the first reviewed OpenChat user and rejects a mismatch with `expectedOpenChatUserId` or a later account switch. Consent UI must display the connected OpenChat account and distinct copy for read and send. `POST /api/connector-delegations/consent` with that JWT and `{transaction, approvedScopes}` consumes the transaction. A read grant is mandatory; send may be omitted. Response is a 303 to the exact callback with one-use `code` and original `state`. There is no token in the URL.
3. RP backend validates `state` against its own pending transaction and posts `{callback, code, state, codeVerifier}` to `/token` with the same Basic client authentication. OpenChat checks client, callback, state, PKCE and two-minute code expiry; any attempt consumes the code. Response: `{access_token, token_type:'Bearer', expires_in:3600, openchat_user_id, scopes}`. Never pass the token through the model, browser URL, tool argument/result, or logs.
4. RP stores the downstream token encrypted and indexed by its own connector client/grant, Thoughtstream user and returned OpenChat user. A note grant never implies an OpenChat grant. It calls `POST /revoke` under the same client authentication with `{connectorGrantId, connectorUserId, openChatUserId}` on disconnect. Revocation invalidates tokens, outstanding codes, and matching pending authorization transactions for that tuple only; note access and other OpenChat grants remain unchanged.
5. A delegated token starts `ocd_`. OpenChat enforces read on `GET /api/chat/conversations`, `GET /api/chat/conversations/:id/messages`, `GET /api/chat/search`; send on `POST /api/chat/conversations/:id/messages`. Any other API route rejects it. Existing chat route membership, blocks and contact discovery remain authoritative. `oc_send_message` requires a caller-stable `clientRequestId`; the OpenChat route derives an opaque message ID from the authenticated client, connector grant/account, OpenChat account, and request ID, independent of token rotation, content, and conversation. It validates stored conversation and exact payload before mutation and preserves exact content. The server suppresses duplicate side effects on retries.

Production persistence addition before enabling: atomically consume transaction/code once across replicas; hash bearer tokens at rest; store scope, client, connector grant/user, OpenChat user, expiry and revocation; validate live revocation on every request. No process-wide API key, client-supplied upstream URL, query-string bearer token, same-email authority or legacy agent-key label can replace this.

## Proposed protected-endpoint patch text (not applied)

- Preserve the existing two note scopes for existing grants/tokens. Extend the exact-two-scope validator intentionally with `openchat.read` and `openchat.send`; never add either scope to a notes-only grant. A token's effective OpenChat permission is the intersection of its current connector grant, its OAuth scopes, and its separately stored OpenChat delegation. Revoked or expired token/grant/delegation fails both `tools/list` and `tools/call`.
- Add only `oc_list_conversations`, `oc_get_messages`, `oc_search_messages`, `oc_send_message` to the controller catalog and dispatcher. List read tools only with effective `openchat.read`; list send only with effective `openchat.send`. Calls recheck the same predicate immediately before resolving the *current request's* encrypted delegation. Reject unknown OpenChat tool names and every unrelated OpenChat REST route. Pass fixed OpenChat upstream origin and per-request bearer to the OpenChat adapter; never use an environment-wide OpenChat user key.
- Add optional OpenChat connection to the existing connector management/consent flow. Exact proposed copy: “Read your OpenChat conversations and messages, including search results, as your connected OpenChat account.” Separate send copy: “Send OpenChat messages as your connected OpenChat account when you ask.” Show the named account before approval and after connection. The read control may be approved alone; send requires a separate affirmative control. Continue notes-only setup without either.
- Persist the outbound OAuth transaction under signed-in Thoughtstream user, connector client/grant, requested scopes, random state, PKCE verifier and expected callback. Only the server initiates `/start` and exchanges `/token`. At callback, compare state, client/grant/session, callback and the returned named OpenChat account; fail on account switching or stale/replayed transaction. Store the token encrypted and bound to that tuple. No automatic same-email linking.
- A new scope request triggers explicit authorization rather than silently broadening the old note grant. Reconnect/review must show both app accounts and independently revocable permissions. Disconnect OpenChat calls `/revoke` for only that tuple and hides its tools while preserving notes. Revoking notes need not revoke OpenChat unless the whole connector grant is disconnected; disconnecting the entire connector revokes both independently.
- Tests must cover old notes-only grants; read-only listing and call denial for send; token/grant/delegation revocation; two concurrent users; account switch; code/state/PKCE/replay; exact callback; membership/directory limits; exact message and retry; credential redaction. No production message is part of acceptance.
